# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A local Posit Team environment in Docker Compose: Posit Connect (:3939), Posit Package Manager (:4242) and Posit Workbench (:8787), wired together and integrated with SAS Viya OAuth for the Positron SAS extension (https://posit-dev.github.io/positron-sas-extension/Workbench/Code/viyaOauth). There is no application code or test suite; the "code" is compose config, product config files and two init scripts. `licenses/*.lic` are real license files — never print or copy their contents.

## Commands

```bash
docker compose up -d                          # start / apply compose + env changes
docker compose ps                             # all three services report (healthy)
docker compose logs -f <service>              # connect | package-manager | workbench | connect-init
docker compose up -d --force-recreate <svc>   # after editing a mounted config file
docker compose run --rm connect-init          # re-run Connect provisioning (idempotent)
docker compose exec connect cat /var/lib/connect-bootstrap/admin-password   # Connect admin login (user: admin)
```

Logins: `posit`/`positsas2026` on Workbench (PWB_TESTUSER) and Connect (publisher, created by `connect-init`; override with `POSIT_USER_PASSWORD`), Connect `admin` + generated password above. Health endpoints: `:3939/__ping__`, `:4242/__ping__`, `:8787/health-check`.

Secrets and Viya settings come from `.env` (template: `.env.example`).

## Architecture

**Images** are pinned to explicit `<version>-ubuntu-24.04-std` tags and are amd64-only (`platform: linux/amd64`; emulated on Apple Silicon, so startup is slow). Several config values are tied to the tag and must be updated together when bumping it:
- R/Python paths in `config/connect/rstudio-connect.gcfg` (`[R]`, `[Python]`) and `config/ppm/rstudio-pm.gcfg` (`RVersion`, `PythonVersion`) — check with `docker run --rm --entrypoint ls <image> /opt/R /opt/python`.
- The distro codename (`noble`) in Package Manager binary URLs in `repos.conf` and the Connect `RPackageRepository` entries. Workbench's `rstudio-server version` says "Jammy" but the container OS is noble — check `/etc/os-release`, not the version string.

**Networking:** inside containers, services reach each other by compose service name (`http://package-manager:4242`, `http://connect:3939`); `Server.Address` values use `localhost` because they are the URLs the browser sees. Connect's publishing token-claim and OAuth redirect URLs are built from `Server.Address`.

**Licenses:** each image's `startup.sh` copies the mounted `.lic` into its data dir (no activation-slot lease); no license env vars are used.

**Workbench config is mounted file-by-file**, never as a whole `/etc/rstudio` directory — the image ships ~25 files there (launcher config, `r-versions`, Positron/VS Code settings) that must stay. Only `repos.conf`, `rsession.conf`, `launcher-env` (image default plus CA env vars for sessions), `positron.extensions.conf` (image default plus `posit.positron-sas`) and `/etc/pip.conf` are overridden. Extensions in `positron.extensions.conf` are installed from Open VSX into each user's `~/.positron-server/extensions` at Positron session start (`/usr/lib/rstudio-server/extras/scripts/install-positron-ext.sh`), because `positron.conf` sets no global `extensions-dir`. The 3 `rstudio-launcher ... Permission denied` errors at startup also occur in the stock image and are harmless.

**SAS Viya OAuth — two different mechanisms:**
- *Workbench* (`config/workbench/pwb-init.sh`, set as the container entrypoint, then `exec`s the image's `entrypoint.sh`; `command` restates the image CMD because overriding `entrypoint` clears it): writes `/etc/rstudio/oauth-clients.conf` from `VIYA_HOSTNAME`/`WORKBENCH_VIYA_CLIENT_ID`/`WORKBENCH_VIYA_CLIENT_SECRET`, encrypting the secret with `rstudio-server encrypt-password`, then unsets the secret before handing over. It also persists launcher keys in the `workbench-shared` volume (`secure-cookie-key`/`session-rpc-key` already live there; the script creates `secure-cookie-key` first on a fresh volume so the encrypted secret stays decryptable).
- *Connect* stores OAuth integrations in its database, so they are created via API by the one-shot `connect-init` service (`config/connect/connect-init.py`, stdlib Python, runs in the Connect image after Connect is healthy). It gets an admin API key via Connect's `[Bootstrap]` endpoint (only works while Connect has zero users; the secret key is generated by the inline `entrypoint` of the `connect` service into the `connect-bootstrap` volume), creates a password-login `admin` (the bootstrap user takes the "first user becomes admin" slot), then creates or PATCHes the integration named `SAS Viya (Viewer)` from `CONNECT_VIYA_CLIENT_ID`/`CONNECT_VIYA_CLIENT_SECRET`.
- *Positron SAS extension profile*: `pwb-init.sh` also merges a default `SAS.connectionProfiles` (profile `viya`, REST, `https://VIYA_HOSTNAME`, optional `POSITRON_SAS_CLIENT_ID`/`_SECRET`) into `/etc/rstudio/positron-user-settings.json`, or removes it when `VIYA_HOSTNAME` is unset. Workbench merges that template into each user's settings at Positron session start without overriding existing keys, so a user who already got the profile keeps their version even if the template changes later. The extension's default `authentication: auto` picks the Workbench OAuth integration whose token URL matches the endpoint.
- `VIYA_HOSTNAME` is shared; each product enables its integration only when its own client ID/secret is set. Partially set values make that product fail fast. Workbench scopes are comma-separated, Connect's are space-separated (the script converts `VIYA_SCOPES`).

**Optional custom CA certs:** `./certs` (empty except a README by default) is mounted into Workbench and Connect; `config/shared/install-ca-certs.sh` runs at their startup (from `pwb-init.sh` / the connect entrypoint) and adds any `*.crt`/`*.pem` (PEM chains or DER) to the system trust store, or removes previously added ones. Python `requests` and Node.js ignore the system store, so `REQUESTS_CA_BUNDLE`/`NODE_EXTRA_CA_CERTS` point at the system bundle: for Connect content via the `connect` service env (inherited by content), for Workbench sessions via `launcher-env`.

## Windows (WSL2)

The same `docker-compose.yml` runs unchanged under Docker Desktop (WSL2 backend) or Docker Engine inside a WSL2 distro; amd64 images run natively on x86 Windows, and published ports are reachable at `localhost` from the Windows browser, so the OAuth redirect URIs stay the same. Requirements:
- Keep the project in the WSL filesystem (e.g. `~/sas-mcp-env`), not `/mnt/c/...`: bind mounts from the Windows drive are slow and lose Linux permissions.
- LF line endings: `.gitattributes` enforces them for git checkouts; files copied or edited with Windows tools can still get CRLF (check with `file config/workbench/pwb-init.sh`, fix with `sed -i 's/\r$//'`).
- Give WSL enough memory (`%UserProfile%\.wslconfig`, `[wsl2] memory=8GB` or more).
- Scripts are started via `bash <script>`/`python3 <script>`, so they don't need the executable bit.

## Gotchas
- `PWB_TESTUSER_UID` must stay set: without it the Workbench image's `startup.sh` re-runs `useradd` on `docker compose restart` and supervisord gives up (restart loop).

- The user's shell exports `CONNECT_API_KEY` for another server, and compose interpolates host env vars — don't introduce compose variables with generic names like that (hence `CONNECT_INIT_API_KEY`).
- Connect bootstrap is irreversible on the real instance (creates users). Experiment in a throwaway `docker run` container instead. The JWT must be HS256 with the base64-decoded key and claims `iss=rsconnect-python`, `aud=rsconnect`, `scope=bootstrap`, sent as `Authorization: Connect-Bootstrap <jwt>` to `POST /__api__/v1/bootstrap`.
- Connect rejects weak passwords (e.g. `posit`) when creating users via API. `[Password] MinimumScore = 0` does not help (0 seems to act as unset), so the shared demo password is `positsas2026`.
- `$` in compose `entrypoint`/`command` strings must be written `$$`.
- If a bind-mount source file doesn't exist, Docker creates an empty directory at that path on the host — delete it before creating the file.
- Find undocumented product settings by grepping the binaries' embedded docs, e.g. `strings /opt/rstudio-connect/bin/connect | grep 'doc:"'`; default configs are in the images under `/etc/rstudio-connect`, `/etc/rstudio-pm`, `/etc/rstudio`.
